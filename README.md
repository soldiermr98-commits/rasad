# رصد — Rasad

افزونهٔ آمار محلی و بدون کوکی برای وردپرس، با رابط فارسی، تقویم شمسی و گزارش فروش ووکامرس. PHP 7.4+ و WordPress 5.8+؛ داده‌ها روی همان سرور ذخیره می‌شوند.

## نصب و استفاده

پوشهٔ افزونه را نصب و فعال کنید. در «رصد ← تنظیمات» وضعیت بافر، کرون و سلامت را بررسی کنید. جمع‌آوری مستقیم از `collect.php` با SHORTINIT انجام می‌شود؛ REST مسیر جایگزین قابل انتخاب است. در سرورهای کم‌بازدید بهتر است کرون واقعی سرور دستور `wp rasad aggregate` را هر دقیقه اجرا کند.

داشبورد شامل مقایسهٔ دوره‌ها، نمودار، صفحات برتر/ورود/خروج، نوشته‌ها و نوع محتوا، منابع ورودی و کمپین‌ها، جستجوی داخلی، کشور/شهر، دستگاه/مرورگر/سیستم عامل، گزارش زنده و فروشگاه است. شهر نیازمند پایگاه GeoIP شهر است؛ نام شهرهای تاریخی که قبلاً فقط هش آن‌ها ذخیره شده قابل بازیابی نیست. انتخاب‌گر شمسی محلی است و هفته را از شنبه آغاز می‌کند. CSV روزانه، صفحات، ابعاد و فروشگاه با دسترسی مدیریتی و nonce، در دسته‌های ۵۰۰ ردیفی صادر می‌شود.

## صحت آمار و حریم خصوصی

شناسهٔ بازدیدکننده، HMAC روزانهٔ IP و UA با رمز محلی است. کوکی یا شناسهٔ مرورگر ذخیره نمی‌شود. IP به‌طور پیش‌فرض قبل از ورود به بافر ناشناس می‌شود؛ UA فقط موقتاً در بافر باقی می‌ماند. خاموش‌کردن ناشناس‌سازی، IP خام را موقتاً در بافر نگه می‌دارد. مسیرها از سیاست فهرست مجاز پارامترها عبور می‌کنند. بازدیدکنندگان یک بازه حاصل جمع بازدیدکنندگان یکتای هر روزند، بنابراین یک نفر در چند روز می‌تواند چند بار در این عدد شمرده شود.

فایل‌های داده با قواعد Apache محافظت می‌شوند. روی Nginx باید دسترسی HTTP به پوشهٔ `wp-content/uploads/rasad/` را با تنظیم سرور ببندید. GeoIP دانلود اختیاری خارجی دارد؛ ردیابی و گزارش‌گیری وابستگی خارجی ندارند.

## ووکامرس

بازدید محصول از beacon مرورگر ثبت می‌شود تا صفحهٔ کش‌شده نیز شمارش شود. افزودن به سبد، تسویهٔ کلاسیک و سفارش پرداخت‌شده ثبت می‌شوند. انتساب سفارش هنگام ساخت سفارش با WooCommerce CRUD (سازگار با HPOS و سفارش Blocks) ثبت می‌شود؛ webhook پرداخت از Referer خودش استفاده نمی‌کند. سفارش‌های قدیمی بدون انتساب، مستقیم/نامشخص هستند. شروع تسویهٔ Blocks فعلاً شمارش جداگانه ندارد.

جدول `rsd_wc_orders` صف پایدار و دفتر جلوگیری از تکرار خرید است: شناسهٔ سفارش یکتا است و ثبت خلاصه‌ها و وضعیت پردازش در یک تراکنش InnoDB انجام می‌شود. payload پس از پردازش پاک می‌شود؛ شناسهٔ سفارش برای جلوگیری از بازپخش بعد از پایان نگهداری دادهٔ خام باقی می‌ماند. این جدول شامل اطلاعات مشتری نیست. حذف کامل داده با گزینهٔ حذف هنگام uninstall انجام می‌شود.

گزارش‌ها از `rsd_wc_daily` و به تفکیک ارز، روز، محصول و ارجاع‌دهنده خوانده می‌شوند. ارزها با هم جمع نمی‌شوند. مبلغ کل سفارش شامل مالیات/ارسال است؛ مبلغ محصول، جمع تخفیف‌خوردهٔ ردیف‌ها بدون مالیات/ارسال است. «واحد ردیابی‌شده» شامل تعداد افزوده‌شده به سبد و تعداد خرید است؛ تعداد سفارش جداست. درآمد، خرید پرداخت‌شدهٔ اولیه است و تغییرات بعدی بازپرداخت از آن کسر نمی‌شود.

## Performance notes

- tracker برابر ۹۴۲ بایت در نسخهٔ تست‌شده است، بدون کتابخانه/CDN و با بارگذاری defer. نمودار SVG است؛ uPlot اضافه نشده تا وابستگی و حجم اضافه نشود.
- گزارش‌های معمولی از جدول‌های خلاصه خوانده می‌شوند و کش نسخه‌دار دارند؛ گزارش زنده به وضعیت نشست‌های اخیر نیاز دارد. CSV از keyset pagination استفاده می‌کند.
- بافر فایل به‌جای بازنویسی کل صف در هر دسته، مکان خواندن را ذخیره می‌کند؛ نوشتن و خواندن هم‌زمان قفل دارند. پاک‌سازی دیگر صف پردازش‌نشده را به‌علت عبور از ۸ مگابایت حذف نمی‌کند. OPTIMIZE TABLE پیش‌فرض خاموش است؛ نگهداری سنگین باید آگاهانه انجام شود.
- APCu کلیدهای جدا برای هر سایت و قفل محلی دارد؛ Redis از RPUSH و Lua اتمیک برای برداشت دسته استفاده می‌کند؛ DB fallback برداشت تراکنشی دارد. فعال‌بودن واقعی Redis/APCu روی هر سرور باید بررسی شود.
- آزمون XAMPP محلی: همهٔ endpointهای گزارش ۲۰۰ با SQL بدون خطا؛ زمان پاسخ ۳ تا ۲۹ میلی‌ثانیه روی دادهٔ کوچک. در آزمون جداگانه با یک میلیون ردیف خام، چهار query نمایندهٔ خلاصه median حدود ۰٫۱۷ تا ۰٫۲۲ و max حدود ۲٫۱۱ میلی‌ثانیه داشتند. این آزمون، خلاصه‌های پرتعداد یا بار هم‌زمان را شبیه‌سازی نمی‌کند.
- دریافت مستقیم HTTP روی همین XAMPP در ۲۰ درخواست، median حدود ۴۹ میلی‌ثانیه داشت. هدف کمتر از ۱۰ میلی‌ثانیه در این محیط تأیید نشده است؛ این اندازه‌گیری کل رفت‌وبرگشت HTTP است. عدد سریع‌بودن را بدون اندازه‌گیری روی سرور مقصد تضمین نمی‌کنیم.

## محدودیت پایداری بافر

خریدها صف پایدار جداگانه دارند. بافر عمومی با قرارداد destructive `pop_batch` در صورت مرگ پردازش پس از برداشت و قبل از ثبت آمار، می‌تواند دستهٔ جاری را از دست بدهد. فشرده‌سازی قطع‌شدهٔ فایل می‌تواند دادهٔ مصرف‌شده را بازپخش کند. APCu با restart/eviction از دست می‌رود و پایداری Redis به تنظیم سرور وابسته است. آزمون هم‌زمانی عادی پاس شده؛ این به معنی تحویل exactly-once در خرابی برق/پردازش نیست. کلیدهای کش قدیمی سراسری به‌علت انتساب مبهم بین سایت‌ها خودکار منتقل نمی‌شوند.

## تست‌ها

```text
php tests/run-tests.php
php tests/test-jalali-roundtrip.php
node tests/test-dashboard-client.js
php tests/test-dashboard-export.php
php tests/test-buffer-concurrency.php
php tests/test-woocommerce-integration.php
```

تست فایل از چند پردازش واقعی استفاده می‌کند؛ تست APCu از شبیه‌ساز فایل مشترک و Redis/DB از fake استفاده می‌کند. برای تست محیط واقعی لوکال (ابتدا در محیط آزمایشی):

```text
php tests/local-smoke.php C:/xampp/htdocs/sks/wp-load.php
php tests/local-commerce.php C:/xampp/htdocs/sks/wp-load.php
php tests/local-benchmark.php C:/xampp/htdocs/sks/wp-load.php
```

benchmark جدول‌های مستقل موقت می‌سازد و در finally حذف می‌کند؛ commerce از شناسه و ارز مصنوعی استفاده می‌کند و fixture خودش را پاک می‌کند. این ابزارها را روی دیتابیس تولید اجرا نکنید. فایل‌های تست داخل CLI محدود شده‌اند. ترجمه‌ها در `languages/rasad.pot` هستند.
